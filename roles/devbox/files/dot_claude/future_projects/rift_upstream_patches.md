## Зачем это вообще

Rift выбран вместо AeroSpace. Он закрывает почти все мои требования, но в нескольких местах
его поведение расходится с ними. Обойти это можно двумя способами:

1. **Держать свой форк Rift.** Это дорого: главный файл `src/actor/reactor.rs` (около 262 КБ)
   меняется почти в каждом релизе, а релизы выходят 1–2 раза в неделю. Каждый мой патч
   пришлось бы перебазировать постоянно, тратя время и LLM-токены, а этого я как раз хочу
   избежать.
2. **Отдать небольшие патчи автору Rift (upstream).** Если их примут, я получаю нужное
   поведение в штатных релизах и ничего не сопровождаю сам.

Поэтому идея такая: оформить проблемы как issue, а где есть смысл, прислать PR. Пока патч не
принят, живём на обходных решениях (они описаны у каждого пункта).

Автор Rift практически один (acsandmann: 937 коммитов, следующий участник: 9). Значит,
принятие полностью зависит от его позиции. По issue #661, #402 и #562 видно, что «следовать
за активированным приложением» он считает фичей, а не багом. Поэтому патч надо предлагать
как **опцию**, а не менять поведение по умолчанию.

Ссылки на код ниже даны по тегу v0.8.6 (2026-11-22). Перед работой их надо перепроверить на
актуальном `main`.

## Патч 1. Политика «не переходить за фоновой активацией» (главный, нужен для must-have)

**Какую мою проблему решает.** Требование «фоновая активность приложения не должна
переключать текущий workspace» (приоритет «очень высокий»). Сейчас, если фоновое приложение
активируется (например, Claude или ChatGPT перезапустились после обновления, или AWS VPN
открыл в браузере страницу повторной авторизации), Rift сам переключает меня на workspace,
где лежит окно этого приложения. Работа, которую я делал, уезжает с экрана.

**Как сейчас устроено в коде.**
- Активация приложения → `Event::ApplicationActivated` (`src/actor/app.rs:2187-2190`).
- Reactor вызывает `auto_switch_to_window_workspace` (`src/actor/reactor.rs:1559-1580`,
  сама функция `5213-5300`).
- Отключить можно только поприложенческим списком `auto_focus_blacklist`, по точному
  bundle ID (`src/common/config/types.rs:566-575`). Глобальной настройки нет.
- При этом в коде уже есть похожий механизм: после пробуждения из сна Rift ставит флаг
  `suppress_auto_workspace_switch_until_input` и не переключает workspace, пока я не нажму
  клавишу или не пошевелю мышью (`reactor.rs:1480-1490`, сброс `1355-1360`, `1465-1470`).

**Что предложить.** Настройку `follow_app_activation = "always" | "explicit"`:
- `always` — текущее поведение, по умолчанию (чтобы не ломать других пользователей);
- `explicit` — переходить, только если активация случилась примерно в течение 750 мс после
  моего явного действия: Cmd+Tab или Cmd+\`, клик мышью (в том числе в Dock), команда Rift.
  Это ровно моя политика: явный выбор окна переключает workspace, фоновая активность нет.
  Оговорка: клик по ссылке в текущем окне тоже считается явным действием, и Rift перейдёт
  в браузер. Это нормально, это и есть моё намерение.

**Аргумент для автора.** В его же коде защита после пробуждения сформулирована так: «Only real
input makes a subsequent activation a trustworthy request» (`reactor.rs:1471-1476`). Патч
обобщает этот принцип и включается только явно.

**Где в коде:**
- `src/actor/input.rs:815-821`: сейчас нажатие клавиши уходит как голый `KeyboardInput`,
  надо передавать клавишу и модификаторы или хотя бы помечать Cmd+Tab;
- проверка метки времени в `auto_switch_to_window_workspace` (`reactor.rs:5213-5300`);
- настройка в `types.rs`;
- тесты в `src/actor/reactor/tests.rs`.

**Размер:** примерно 60–100 строк вместе с тестами.
**Есть ли уже issue или PR:** на 2026-11-25 не нашлось (искали по issues и PR acsandmann/rift).
**Шансы:** средние. Автор считает следование за активацией фичей (#661, #402, #562 просили его
усилить), но опция не меняет поведение по умолчанию.
**Если откажут:**
- чёрный список `auto_focus_blacklist`: Claude (`com.anthropic.claudefordesktop`), ChatGPT
  (`com.openai.codex`; старый «ChatGPT Classic» — `com.openai.chat`). Плюс app rules,
  которые кладут их окна на workspace AI. Минус: для приложений из списка перестают работать
  и явные Cmd+Tab и клик в Dock (Rift не переходит на их workspace);
- AWS VPN: активируется не VPN-клиент, а браузер по умолчанию (новая вкладка в существующем
  окне), поэтому чёрный список тут не помогает. Решение: Hammerspoon как обработчик http(s),
  который открывает URL от VPN-клиента (`com.amazonaws.acvc.osx`) в **новом** окне браузера.
  Новое окно попадает на текущий workspace, переключения нет, страница логина видна. Около
  40 строк Lua;
- либо держать патч локально: сборка через cargo, подпись, перебазирование `reactor.rs`
  почти на каждый релиз (только после v0.8.6 его уже меняли 6 коммитов), возможно повторная
  выдача прав Accessibility после каждой пересборки (не проверено).

## Патч 2. Повтор команды при удержании клавиши (опционально)

**Какую мою проблему решает.** Требование «непрерывное изменение размера окна при удержании
клавиши». Сейчас Rift отбрасывает события автоповтора клавиатуры
(`src/actor/input.rs:1155-1166`): если зажать клавишу resize, сработает только первый шаг.

**Что предложить.** Опцию на уровне отдельного binding (например, `repeat = true`), чтобы
автоповтор разрешался только для выбранных команд (resize), а остальные команды по-прежнему
не повторялись случайно. Отбрасывание повтора в коде объяснено тем, что переключатели
(toggle) не должны «мигать» при удержании, поэтому именно opt-in на binding, а не общий флаг.
**Где в коде:** то же место в `input.rs` и разбор binding в `src/common/config/parse.rs`.
**Размер:** примерно 30–60 строк.
**Шансы:** довольно высокие, поведение по умолчанию не меняется.
**Если откажут:** менять размер нажатиями в режиме Resize (каждое нажатие — один шаг).
Это терпимо.

## Патч 3. Проверка конфига без запуска Rift (опционально, но полезно для Ansible)

**Какую мою проблему решает.** Требования «проверка конфигурации перед применением» и
«сохранение предыдущей рабочей конфигурации при ошибке».
- При hot reload Rift отклоняет битый конфиг и оставляет старый
  (`src/actor/config.rs:244-253`), это хорошо.
- Но **при старте** Rift на битом конфиге падает (`Config::read(...).unwrap()`,
  `src/bin/rift.rs:174-178`), а launchd с KeepAlive перезапускает его по кругу. Значит,
  если Ansible положит битый конфиг, после следующего входа в систему WM не будет.
- Флаг `--validate` проверяет только файл раскладок и срабатывает после проверки прав
  Accessibility (`rift.rs:155-170`), то есть в Ansible его не вызвать.

**История.** PR #461 «feat(cli): add offline config check» (`rift config check --config PATH`)
**закрыт без слияния 2026-10-05**, автор Rift его не прокомментировал. Значит, сам по себе
офлайн-чек он, возможно, не хочет.

**Что предложить.** Вариант поменьше: при битом конфиге на старте не падать, а записать
ошибку в лог и стартовать с конфигом по умолчанию. Это 10–20 строк в `rift.rs` и закрывает
главный риск (падение по кругу). Офлайн-чек упомянуть в issue как желаемое, но не настаивать.
**Шансы:** неясны, см. #461.
**Если откажут:** в Ansible деплоить конфиг с резервной копией, вызывать
`rift-cli execute config reload` (на битом файле он возвращает ошибку,
`src/actor/config.rs:252`) и при ошибке возвращать старый файл (это и так в плане). Это
защищает деплой, но не ручные правки конфига.

## Патч 4. Правильная привязка событий к workspace (issue, возможно баг)

**Какую мою проблему решает.** Индикатор активности в SketchyBar («в неактивном workspace
что-то произошло»).
- `windows_changed` публикуется только для **активного** workspace
  (`reactor.rs:3249-3285`).
- `window_title_changed` и `focused_window_changed` несут ID и имя **активного** workspace,
  а не того, где лежит окно (`reactor.rs:3294-3325`).

**Что предложить.** Сначала issue: похоже на баг. В событии должен быть workspace самого
окна. **Размер:** примерно 20–40 строк. **Шансы:** высокие, это исправление бага.
**Если не исправят:** подписчик в Hammerspoon сам ведёт карту «окно → workspace» через
`rift-cli query workspaces`. Работает, просто кода больше.
