## Receiving use and sufficient result

The receiving work is authoring and qualification of a fuzzing agent and six skills for Claude Code
and Codex; [[repository-placement]] and [[authoring-validation]] record the current implementation.
The present result is a connected methodology: new corpora and exploratory directions, persistent
research identity, scoped operations, pause/resume/closure and independent checks across sessions.
It is sufficient for that use when each rule has a basis, a home and a check; it need not close every
research question. Advanced invocation policy and behavioural qualification remain separate from authoring.

## Source contribution, destination and return

F.0.2.MA allocates content by the operation it changes. C.39 then checks whether those operations
actually connect; a source-to-document mapping alone does not establish an executable method.

| Contribution | Destination and retained condition | Material left at its source |
|---|---|---|
| Bounded reconnaissance and branching search | Charter, campaign and structured-input operations; material and possible contribution suffice before an exact hypothesis exists | RMP.1/C.40 theory and research provenance; no obligation to implement every search family |
| Fuzzing Book seeds, grammar/repair and reduction | Structured-input and language skills; retain malformed-input paths, bounded construction, replay and same-symptom checks | R4–R6 chapter ledgers and worked examples; book coverage is not local effectiveness evidence |
| Native engine execution and artefacts | Go, Python and Rust operation contracts; qualify actual execution, checks, encoding and replay on the selected toolchain | Version-specific manuals and unresolved facts; no universal counter semantics |
| Failed go-kdl2/proj attempts | Defeating cases in [[research-lifecycle-cases]] and eval families D/G/H | Historical records and causal uncertainty; their workflows are not adopted as successful designs |
| Persistent work and useful corpus | Agent/campaign own continuation and decisions; language/structure skills return the actual inputs and unfinished operation | Existing repository evidence/checkpoint conventions; no new memory service |
| Provider loading and size rules | [[authoring-budgets]] and authored provider definitions | Dated official pages; shared skill meaning does not establish identical loading or permissions |

Change an allocation when its source premise, receiving operation or provider behaviour changes.
Reuse unaffected contributions. New terminology or another source passage alone does not create a
new skill. Keep the six agreed responsibilities; invocation remains a separate decision.

## Construction and checking

1. Recover the contribution and its conditions from sources; keep supported claims and proposed
   adaptations distinct (F.0.2.MA, RMP.7).
2. Follow the new-corpus case from available material through a useful result. Repair missing joins,
   such as how generated seeds become replayable engine inputs, at their owning operation (C.39).
3. Express the shared orchestration in [[agent-procedure]] and reusable operations in the six skill
   contracts. Each operation supplies inputs, actions, outputs, limits and a counterexample (SYSE.47/48).
4. Shorten only after those actions and conditions are clear. Link conditional details where needed;
   compare the short version with its source and actual receiving use (F.19, A.6.3.CSC).
5. Test the configured implementation on both legitimate continuation and unjustified repetition.
   Address a demonstrated defect or worthwhile improvement and compare behaviour under the same
   declared conditions (SYSE.46, E.23).

This is an authoring method, not a mandatory FPF checklist for every fuzz run. Initial exploration
does not require knowing its discovery in advance; legitimate new questions can coexist with closed
old ones. A local process limit still does not settle the research question.

`G.2` describes the historical source portfolio, not a demand to broaden it now. `SIE.4` is reserved
for the later correspondence between shared operations and each provider's actual facilities.
`KCAE.CHANGE` adds no necessary result for this bounded revision and is not applied.

## Result test

- **Result kind:** amended methodology and an evaluation specification, not observed effectiveness.
- **Receiving use:** authored agent/skills and bounded qualification under [[next-iteration]].
- **Binding:** evidence → amended rule → operation → independent check in [[methodology-review]].
  The authoring stage must establish provider compatibility; the evaluation stage must establish
  persistent-state recovery, justified closure/continuation and useful work. Neither follows from
  writing these notes.

## Binding for the 2026-11-11 correction

The earlier B/R rule was our mistaken translation of the user's stopping requirement. The governed
object is research per commit/experiment/dataset, not process lifetime. C.11.DUA :4.1–4.4 and :7
bound further inquiry; C.11.DBR :4.1–4.5 governs changed bases; SYSE.43 :4.1–4.4 and :7 governs
faithful recording, retrieval and receiving use; SYSE.47 :4.2–4.3 and :4.5 covers repeated/delayed
use without unwarranted repetition. [[research-lifecycle-cases]] binds these methods to concrete
negative evidence. The state names in [[stopping-algorithm]] are this design's contract, not terms
claimed to be prescribed by FPF. Invocation policy remains deferred.
