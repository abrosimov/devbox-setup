# Applicability gate

This is a methodological assessment of a named target after work has been authorised. It does
not define when an agent or skill is invoked; invocation and routing remain deferred.

The assessment produces `fuzz(method, oracle)`, `do-not-fuzz(reason)`, or
`out-of-scope(reason)`, supported by the target contract and repository evidence. These are
assessment results, not research states. Recover prior assessments and their assumptions first;
reassess only what the current commit/experiment/dataset changes. [[stopping-algorithm]] governs
justified continuation, closure and reuse across invocations.

When the target or input behaviour is not yet understood, first make a scoped reconnaissance of
concrete code, corpus or contract material. State the operation and learning aim without requiring
a precise hypothesis or pre-proven yield. Return observed distinctions and a candidate target,
or the missing basis. This preparatory result does not claim that a harness or oracle is qualified.

## Assess a concrete target

| Question | Evidence required | Consequence |
|---|---|---|
| What behaviour matters? | Entry point, input domain, plausible failure class and product contract | If these cannot be established by a justified scoped assessment, report the missing basis; do not invent an adversary or expand the project |
| Is there a useful fuzzing experiment? | A byte/text/primitive/encoded-sequence input path and an executable oracle | Choose the least elaborate suitable fuzz harness; a typed input is not itself a reason to reject fuzzing |
| Can an input be replayed? | Resettable state, explicit setup, controlled time/randomness and dependencies | Persistent state or environmental dependence needs a bounded isolation arrangement; otherwise record the blocker |
| Is the next work bounded and meaningful? | Concrete material and operation, possible learning contribution or question-led observation, end condition and practical resource limits | Reconnaissance can discover the question; low throughput alone does not reject a target |
| Does the target exercise product behaviour? | Known valid and invalid examples reach the intended calls and checks | A rejecting harness can be defective or correctly reject those examples; inspect the contract before deciding |
| Is this work in scope? | Authorised boundaries, existing toolchain and six skill responsibilities | PBT, mutation analysis, infrastructure expansion and product repair are excluded |

Network, filesystem and process use are relevant to isolation and reproducibility, not a blanket
claim that every such API is unfuzzable. Do not refactor production code to manufacture an
in-scope target. A finite enumerable domain or a wrapper with no relevant behaviour may warrant
`do-not-fuzz`; explain that local judgement without asserting a universal yield law.

## Select a method and oracle

| Target evidence | Candidate experiment | Important condition |
|---|---|---|
| Parser, decoder or format reader | Engine-generated bytes/text, representative seeds, token dictionary where supported | Expected rejection is distinct from a product failure |
| Checksums, recursive syntax or encoded structures block useful inputs | Bounded structured seeds, fuzzing-side decoder or repair, as in [[input-shape-triage]] | Preserve an invalid-input path and account for preparation cost |
| Two implementations share a specified domain | Differential fuzzing | Normalisation, unspecified behaviour and reference limitations are explicit |
| Encoder/decoder pair | Round-trip or canonicalisation check | Equality matches the contract; serialised spelling need not be identical |
| FFI or unsafe boundary | Instrumented harness and relevant memory/resource checks | Instrumentation and permitted calls are verified for the actual toolchain |
| Resettable operation sequence | Bounded byte-decoded sequence with existing contract checks | Building a separate model-testing project is outside this task |

Use [[oracle-ladder]] to choose justified checks. Do not claim that an upstream fuzzing campaign
proves a wrapper safe, that memory safety eliminates all relevant failures, or that absence of
new coverage proves a harness unusable. The earlier research summaries are source material, not
validated universal thresholds. The deliverable is the assessment and, if suitable, the charter
in [[fuzzing-charter]], tested by [[eval-family-A-gate]].
